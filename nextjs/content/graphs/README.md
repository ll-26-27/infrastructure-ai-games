## A flash card, a row, a node

Take one idea from the course: Susan Leigh Star's claim that infrastructure becomes visible when it breaks.

**As a flash card**, it is a name on the front and a sentence on the back. You can memorize it. You can know every card in the deck and still not see anything differently.

**As a row in a table**, it gets fields: who said it, in which reading, on which page, for which week, how sure we are. Now you can sort it, filter it and count it. This is what you started building on September 28, when you turned the course into cards and the cards into a database.

**As a node in a graph**, it gets links: Star's reading *introduces* it, Hasan's account of data repair *contrasts with* it ("not a stark infrastructural breakdown"), and a game mechanic, the cascade failure, breaks infrastructure on purpose. A graph is still just two tables, one of nodes and one of edges. The difference is that the links carry the meaning, and you can follow them somewhere you didn't plan to go.

Each graph on this site can be shown all three ways. Switch between *Graph*, *Table* and *Flash cards* at the top of it and watch what each view lets you see.

## Two graphs and a machine for joining them

One graph is the course: its weeks, readings, thinkers and concepts. The other is games: mechanics, the games that use them, the games those came from, and the technologies they ran on. Every page in [Mechanics](/mechanics) and the [Gallery](/gallery) is a node in the games graph, so the graph grows when you add a page.

This repository is a machine for bringing the two into contact. Pick an idea from one side and a thing from the other and ask where they meet. A good point of contact is not a match. It is a claim you can test, and it usually breaks somewhere interesting.
